# Практична робота №8 (варіант 9, Форум): безпека застосунку

Фінальна, захищена версія застосунку «Форум» (таблиця `topics` з практикуму №4): сторінки з практикуму №4,
доменна дія `pin` і API з практикуму №6 зібрані в одній папці з усіма виправленнями за результатами аудиту
практикумів №1–7.

## Файли

| Файл | Призначення |
|------|-------------|
| `bootstrap.php` | Спільна основа: сесія, заголовки безпеки, функції `e()`, `csrf_token()`, `verify_csrf()`, `require_moderator()`, `require_post()`, `validate_topic()`, `abort()`, обробник винятків |
| `config.php` | Параметри підключення до БД і хеш пароля модератора |
| `db.php` | Підключення PDO (винятки, справжні підготовлені запити) |
| `index.php` | Список тем, фільтр за автором, форма створення теми; кнопки «Закріпити», «Видалити», «Редагувати» бачить лише модератор |
| `add.php` | Створення теми (POST + CSRF-токен + серверна валідація) |
| `edit.php` | Редагування теми (лише модератор, POST + CSRF) |
| `pin.php` | Закріплення теми (лише модератор, POST + CSRF) |
| `delete.php` | Видалення теми (лише модератор, POST + CSRF, підтвердження в браузері) |
| `login.php`, `logout.php` | Вхід і вихід модератора |
| `api.php` | API з практикуму №6 із захистом (CSRF, права модератора для `pin`); токен видає `GET api.php?resource=csrf` |
| `app.js` | Підтвердження перед видаленням (окремий файл, бо політика CSP забороняє вбудовані скрипти) |
| `style.css` | Оформлення |
| `csrf_demo/attack.html` | Сторінка для демонстрації CSRF-атаки (див. нижче) |

## Запуск

1. У XAMPP запущено MySQL, база `practicum4` і таблиця `topics` уже існують (практикум №4).
2. ```
   cd D:\php_lab\practicum08
   C:\xampp\php\php.exe -S 127.0.0.1:8000
   ```
3. Відкрийте `http://127.0.0.1:8000/index.php`. Помилки PHP пишуться в лог, а в `php -S` вони з'являються у вікні PowerShell.
4. Вхід модератора: `http://127.0.0.1:8000/login.php`, пароль `moderator123`. Хеш пароля лежить у `config.php`
   (`password_verify`), для зміни пароля згенеруйте новий хеш функцією `password_hash()`.

## Звіт «до / після»

### 1. SQL-ін'єкція (фільтр за автором)

- Payload: `' OR '1'='1`, введений у поле «Автор» (або `index.php?author=' OR '1'='1`).
- До: вразливості немає, запит уже був підготовленим (практикуми №4–7).
- Після (лишається так само, `index.php`, `api.php`):
  ```php
  $stmt = $pdo->prepare('SELECT * FROM topics WHERE author = :author ORDER BY id DESC');
  $stmt->execute([':author' => $author]);
  ```
  У `db.php` додано `PDO::ATTR_EMULATE_PREPARES => false`, тож значення передаються СУБД окремо від тексту запиту.
- Результат перевірки: сторінка показує «Тем не знайдено», без помилок SQL.

### 2. XSS (поле `title` теми)

- Payload: назва теми `<script>alert(1)</script>` і `<img src=x onerror=alert(1)>`.
- До: вразливості немає, виведення вже було екрановане.
- Після (виведення в `index.php` і `edit.php`):
  ```php
  function e(string $value): string
  {
      return htmlspecialchars($value, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');
  }
  ```
  ```php
  <td><?= e($topic['title']) ?></td>
  ```
  Додатковий шар захисту: заголовок `Content-Security-Policy: default-src 'self'` у `bootstrap.php` забороняє вбудовані скрипти.
- Результат перевірки: payload відображається як звичайний текст, вікно `alert` не з'являється, а в коді сторінки (Ctrl+U) видно `&lt;script&gt;`.

### 3. CSRF (закріплення теми модератором)

- Payload: сторінка `csrf_demo/attack.html` із формою, що надсилає `POST` на `pin.php` або `api.php?...&action=pin`.
- До (практикум №6): `POST api.php?resource=topics&action=pin&id=1` без токена закріплював тему, тобто запит із чужого сайту виконувався.
- Після (`bootstrap.php`, `pin.php`):
  ```php
  function csrf_token(): string
  {
      if (empty($_SESSION['csrf_token'])) {
          $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
      }
      return $_SESSION['csrf_token'];
  }

  function verify_csrf(?string $token = null): void
  {
      $sent = $token ?? str_field($_POST, 'csrf_token');
      if ($sent === '') {
          $header = $_SERVER['HTTP_X_CSRF_TOKEN'] ?? '';
          $sent = is_string($header) ? $header : '';
      }
      $expected = $_SESSION['csrf_token'] ?? '';
      if ($expected === '' || !hash_equals($expected, $sent)) {
          abort(403, 'Недійсний CSRF-токен');
      }
  }
  ```
  ```php
  require_post();
  verify_csrf();
  require_moderator();
  ```
  Кожна форма, що змінює дані, містить `<?= csrf_field() ?>`. Для API токен видає `GET api.php?resource=csrf`, і клієнт передає його в заголовку `X-CSRF-Token` або в полі `csrf_token`.
  Права модератора перевіряються окремо (`require_moderator()`), сесійний ідентифікатор оновлюється при вході (`session_regenerate_id(true)`).
- Результат перевірки: запит без токена отримує 403 і тема не закріплюється.

### 4. Незахищена дія: створення теми без обмеження довжини й перевірки на порожній ввід

- Payload: `title` порожній (або понад 100 символів), надісланий напряму, в обхід HTML-форми.
- До: у практикумах №4–7 перевірка вже була на сервері (`$title === ''`, `mb_strlen(...) > 100`). Прогалина знайдена лише в практикумі №2, де поле `message` не мало верхньої межі.
- Після (`validate_topic()` в `bootstrap.php`, використовується в `add.php`, `edit.php`, `api.php`):
  ```php
  if ($title === '') {
      $errors[] = 'Поле title обов\'язкове';
  } elseif (mb_strlen($title) > 100) {
      $errors[] = 'Поле title не може бути довшим за 100 символів';
  }
  ```
  Ті самі перевірки діють для `author`. Значення, що не є рядком (наприклад, масив), перетворюються на порожній рядок функцією `str_field()`, а некоректний `id` дає 400 (`parse_id()`).
- Виправлення для практикуму №2 (`form.php`):
  ```php
  if (mb_strlen($message) < 10) {
      $errors['message'] = 'Повідомлення має містити щонайменше 10 символів';
  } elseif (mb_strlen($message) > 5000) {
      $errors['message'] = 'Повідомлення не може бути довшим за 5000 символів';
  }
  ```
  У полі `textarea` додається `maxlength="5000"`.

### 5. Додатково: GET для дій, що змінюють дані, і помилки сервера

- Видалення, закріплення, редагування й вихід виконуються лише через `POST` (`require_post()`): `GET delete.php?id=1` повертає 405 і нічого не видаляє. Для видалення додано підтвердження (`app.js`, атрибут `data-confirm`). Саме по собі `confirm()` не є захистом, його доповнюють CSRF-токен і перевірка прав.
- Користувач не бачить винятків PHP/PDO: `display_errors` вимкнено, а винятки перехоплює обробник у `bootstrap.php`:
  ```php
  set_exception_handler(function (Throwable $error): void {
      error_log(sprintf('%s: %s in %s:%d', get_class($error), $error->getMessage(), $error->getFile(), $error->getLine()));
      abort(500, 'Внутрішня помилка сервера. Спробуйте пізніше.');
  });
  ```
  До цього `db.php` практикуму №4 виводив текст помилки підключення (наприклад, `Unknown database 'practicum4'`).

## Як перевірити

1. **SQLi:** `http://127.0.0.1:8000/index.php?author=' OR '1'='1` дає «Тем не знайдено».
2. **XSS:** додайте через форму теми з назвами `<script>alert(1)</script>` та `<img src=x onerror=alert(1)>`. Вікна `alert` немає, назви видно як текст.
3. **CSRF, демонстрація в браузері:**
   - Атака «до»: запустіть сервер практикуму №6 на `127.0.0.1:8000`, а в другому вікні PowerShell:
     ```
     cd D:\php_lab\practicum08\csrf_demo
     C:\xampp\php\php.exe -S 127.0.0.1:8001
     ```
     Відкрийте `http://127.0.0.1:8001/attack.html` і натисніть першу кнопку: тема з id=1 закріпиться.
   - Атака «після»: зупиніть сервер практикуму №6, запустіть сервер `practicum08` на порту 8000, увійдіть як модератор і знову натисніть **другу** кнопку на `attack.html`. Відповідь 403 «Недійсний CSRF-токен», навіть попри активну сесію модератора.
   - Порти 8000 і 8001 належать одному «сайту» (`127.0.0.1`), тому cookie сесії в атаці надсилається. Відхиляє запит саме відсутній токен.
4. **CSRF, перевірка в консолі** (потрібен саме `curl.exe`):
   ```
   curl.exe -i -X POST "http://127.0.0.1:8000/pin.php" -d "id=1"
   ```
   Очікується 403.
5. **Валідація в обхід форми (API):**
   ```
   curl.exe -c jar.txt "http://127.0.0.1:8000/api.php?resource=csrf"
   curl.exe -b jar.txt -i -X POST "http://127.0.0.1:8000/api.php?resource=topics" -H "X-CSRF-Token: ВСТАВТЕ_ТОКЕН" -d "title=&author=Ira"
   curl.exe -b jar.txt -i -X POST "http://127.0.0.1:8000/api.php?resource=topics" -H "X-CSRF-Token: ВСТАВТЕ_ТОКЕН" -d "title=Test&author=Ira"
   curl.exe -b jar.txt -i -X POST "http://127.0.0.1:8000/api.php?resource=topics&action=pin&id=1" -H "X-CSRF-Token: ВСТАВТЕ_ТОКЕН"
   ```
   Очікувані коди: 400 (порожній `title`), 201 (тему створено), 403 (`pin` без прав модератора).
6. **GET замість POST:** `http://127.0.0.1:8000/delete.php?id=1` у браузері дає 405, тема не видаляється.
7. **Помилки:** зупиніть MySQL і відкрийте `index.php`: сторінка показує лише «Внутрішня помилка сервера», а деталь (`PDOException ...`) з'являється у вікні `php -S`.

## Обмеження

Вхід модератора має один спільний пароль без обмеження кількості спроб, а токен CSRF один на сесію. Для навчального
застосунку цього достатньо, у реальному проєкті додали б блокування після невдалих спроб, обмеження за IP і HTTPS
(з прапорцем `secure` для cookie сесії).
